PLURALBRIDGE — TERMINOLOGY DICTIONARY (abbreviated for this document)
---------------------------------------------------------------------

TERMS

Plural
A person or collective whose plural structure is represented by a Plural Map.

Plural Map
A Plural Map describes how a plural understands their world.

Object
An entity represented in a Plural Map, including a System, Group, Place, or Member.

Anchor
An object that provides context for operations. Systems, Groups, and Places are anchors.

Placement
A relationship recording where an object appears in a Plural Map, including its parent anchor and ordering. An object may have multiple placements.

Structural membership
A relationship expressing that a member belongs to an anchor.

Access membership
A relationship associating an Account with an object for access purposes.

Role
The function or authority associated with participation in a relationship.

Account
A sign-in identity that can access objects through access membership. An Account is not a System.

Focus
The currently active anchor used as an operational context. Focus does not grant access.

PLURAL MAP EXAMPLES
-------------------

These examples illustrate possible structures, not an exhaustive list of permitted configurations.
Indentation illustrates placement or structural membership; annotations show other relationships or statuses.
A member shown in multiple locations is the same member, not a duplicate.
“Groups” is a collection heading in these diagrams, not an additional object type.

1. Simple Single-System Plural Map
A person signs in and has one System.

├── System: The Harbor
│   ├── Member: A

│   ├── Member: C
│   └── Groups
│       ├── Group: Dancers
│       │   ├── Member: B

This is the simple default: one Account, one System anchor, members and groups inside it, and one focused anchor context.

DESIGN RULES
------------

These examples illustrate the following PluralBridge design rules, grouped by subject.

1. Objects and Anchors
- Object identity consists of object type + object ID.
- Operations such as adding members require an anchor.
- A root anchor has no parent anchor in its root placement; a Plural Map may have multiple root anchors.
- An internal cluster can be represented using an appropriate anchor; it need not be a separate System.
- Archived is an object status, not a relationship type.

2. Placement, Membership, and Relationships
- Placement records where an object appears; structural membership records where a member belongs.
- An object may have multiple placements, and a member may belong to multiple anchors, without creating duplicate objects.
- Parent / child placements describe containment. Sibling, related, associated, and evolving / uncertain relationships describe other connections.
- Relationship arrows indicate direction; a relationship shown without an arrow may be represented by reciprocal directed records.

3. Access, Authority, and Auditing
- Access membership, roles, explicit permissions, consent, and policy govern access.
- Placement, structural membership, and descriptive relationships do not themselves grant access, authority, or visibility.
- Audit policy governs recording of activity.

4. Focus and Fronting
- Focus selects the active anchor context without creating access.
- Fronting is modeled within the focused anchor context.

5. Flexibility and Professional Use
- The default user experience can remain simple while the underlying model supports varied structures, including those with no Systems.
- Therapist-facing views should be user-controlled and privacy-aware.
- Professional input can improve safety without overriding lived experience.
